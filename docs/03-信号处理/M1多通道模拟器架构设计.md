# M1多通道模拟器架构设计

版本：0.3.0；状态：M1-P1A/P1B已落地；P1C–P1D仍为设计。

## 1. 目标

本设计定义M1-P1模拟器的运行时结构、公共数据源接口、确定性时间轴、多通道生成、故障注入顺序、会话记录和重放边界。

核心约束：

- 模拟器直接输出M1-P0冻结的`M1Sample`；
- 模拟器、重放和未来真实硬件共用一个数据源抽象；
- Pulse、Load、PPG共享同一采样时钟和心搏事件；
- 场景真值只用于测试预期，不作为后续正式算法输入；
- 所有随机行为受显式种子控制；
- 真实阈值保持`pending_h1_calibration`。

## 2. 分层架构

```text
配置层
  ScenarioDefinition + ConfigOverride
        ↓
确定性核心
  DeterministicClock + BeatTimeline + RNG streams
        ↓
基础观测层
  PulseModel + LoadModel + PPGModel
        ↓
故障注入层
  Physiological → Channel → Device → Transport → Storage
        ↓
契约适配层
  M1SampleFactory
        ↓
数据源层
  SimulatorDataSource / ReplayDataSource / HardwareDataSource boundary
        ↓
会话层
  SessionRecorder + manifest/events/expected/summary
```

## 3. 公共数据源接口

建议定义：

```python
from collections.abc import Iterator
from typing import Protocol

from digital_pulse.m1_contracts import M1Sample


class M1DataSource(Protocol):
    @property
    def source_type(self) -> str:
        ...

    def samples(self) -> Iterator[M1Sample]:
        ...
```

### 3.1 SimulatorDataSource

职责：

- 接收已验证的`ScenarioConfig`；
- 构造确定性时钟、心搏事件、通道模型和故障计划；
- 顺序产生`M1Sample`；
- 暴露场景、事件和预期摘要给SessionRecorder；
- 不直接实现质量评分或INT动作。

### 3.2 ReplayDataSource

职责：

- 从已保存的`manifest.json`和`samples.jsonl`读取；
- 每条记录反序列化为`M1Sample`并重新验证；
- 保持原始顺序和值；
- 不重新计算随机波形；
- 不根据当前代码重新注入故障。

### 3.3 HardwareDataSource边界

M1-P1只定义未来边界，不实现：

- 接收正式协议帧；
- 将旧`DataSample`或新固件帧适配为`M1Sample`；
- 保留设备时间、主机接收时间和接收完整性；
- 输出与模拟器相同的`Iterator[M1Sample]`。

后续SP、APP、INT只能依赖`M1DataSource`或等价最小接口。

## 4. 配置模型

建议运行时配置分为：

```text
ScenarioDefinition  # 仓库冻结的场景默认语义
ScenarioOverride    # CLI或测试允许覆盖的有限参数
ScenarioConfig      # 合并、规范化和验证后的不可变配置
```

`ScenarioConfig`至少包含：

- `scenario_id`
- `scenario_version`
- `simulator_version`
- `duration_s`
- `sample_rate_hz`
- `random_seed`
- `start_time_utc`
- `channels`
- `physiology`
- `fault_schedule`
- `attempt`
- `output_options`
- `configuration_digest`

### 4.1 配置规范化

配置摘要使用规范化JSON：

- UTF-8；
- key排序；
- 紧凑分隔符；
- 数字采用稳定序列化；
- 不包含输出目录、本机路径和运行日志级别；
- 包含所有影响样本、状态、事件和预期的字段。

算法：SHA-256。

### 4.2 覆盖限制

CLI可以覆盖：

- seed；
- duration；
- sample rate；
- 输出目录；
- 明确列入白名单的场景参数。

CLI不得通过任意JSON覆盖破坏场景核心语义。场景语义边界应在配置验证阶段检查。

## 5. 随机数流

禁止所有组件共享一个随调用顺序变化的全局随机数生成器。

建议从根种子派生独立流：

```text
root_seed
├─ beat_timing_rng
├─ pulse_noise_rng
├─ load_noise_rng
├─ ppg_noise_rng
├─ artifact_rng
└─ transport_rng
```

派生方式必须稳定，例如使用`numpy.random.SeedSequence`或明确的哈希派生。

收益：

- 增加某通道内部随机调用不应无意改变其他通道；
- 可以分别测试心搏、噪声和故障；
- 确定性更易审计。

## 6. 确定性时钟

`DeterministicClock`输入：

- `sample_rate_hz`
- `duration_s`
- `start_time_utc`
- 可选初始`frame_sequence`
- 可选初始`device_time_us`

输出每个样本的：

- `sample_index`
- `frame_sequence`
- `device_time_us`
- `elapsed_time_s`
- `host_received_at_utc`

### 6.1 采样数量

建议使用：

```text
sample_count = round(duration_s * sample_rate_hz)
```

配置验证应限制浮点歧义，并在manifest记录实际样本数和实际末时刻。

### 6.2 设备时间

设备时间以整数微秒表示。对不能整除1秒的采样率，不允许每步简单截断后累计漂移；应根据样本索引从起点计算：

```text
device_time_us = start_device_time_us + round(index * 1_000_000 / sample_rate_hz)
```

### 6.3 主机时间

`host_received_at_utc`由冻结UTC起点加确定性相对时间和可配置接收延迟生成。正常场景必须带时区且单调。

## 7. BeatTimeline

`BeatTimeline`是Pulse和PPG共同的事件级真值。

建议事件结构：

```text
BeatEvent
- beat_index
- onset_time_s
- interval_s
- nominal_amplitude
- morphology_parameters
```

### 7.1 心率模式

M1-P1至少支持：

- 固定心率；
- 受控轻微间期变化；
- 明确配置的漏搏或伪峰仅作用于观测层，不静默改写真实BeatTimeline。

### 7.2 禁止事项

- Pulse和PPG分别生成独立心搏；
- 后处理检测峰后再反推真值；
- 使用真实系统时钟决定心搏位置；
- 将场景预期质量直接写进样本通道。

## 8. 通道模型

## 8.1 PulseModel

输入：

- BeatTimeline；
- 基础形态参数；
- 接触状态；
- Load观测或基础接触因子；
- Pulse独立噪声流。

输出：

- 原始动态通道值；
- 通道状态；
- 削顶状态；
- 可选内部真值摘要，仅写入测试辅助文件。

首版形态应保持可解释和低复杂度，可复用已有P0模板思想，但不得把P0单通道协议对象当作新公共契约。

## 8.2 LoadModel

输入：

- 接触计划；
- 稳态载荷；
- 手动波动；
- 独立噪声流。

输出：

- `load_raw`；
- 通道状态；
- 可选`target_load_raw`，M1手动场景可为空；
- 接触建立/丢失事件。

模拟值只用于软件行为，不能解释为人体安全载荷。

## 8.3 PPGModel

输入：

- BeatTimeline；
- 配置时延；
- PPG形态；
- 独立噪声流。

输出：

- `ppg_raw`；
- 通道状态；
- 削顶状态。

PPG错位、漏搏和伪峰在观测层注入，BeatTimeline保持不变。

## 9. 故障注入分层与顺序

固定顺序：

```text
1. 生理事件层
2. 基础通道观测层
3. 通道故障层
4. 设备状态层
5. 传输层
6. 会话存储层
```

### 9.1 生理事件层

首版仅用于受控心搏间期变化。不得借此模拟未经验证的疾病模式。

### 9.2 通道故障层

- 弱信号；
- 无接触；
- 上下削顶；
- 基线漂移；
- 运动伪影；
- 载荷不稳；
- PPG错位；
- 通道断线。

要求数值、status、clipping flag和事件一致。

### 9.3 设备状态层

- `abort`；
- 通用`device_fault`；
- 传感器状态变化；
- 设备状态转换。

### 9.4 传输层

- frame loss；
- timestamp regression；
- 重复时间戳；
- 可选时间跳变。

传输层在M1Sample生成边界处理，不回写BeatTimeline。

### 9.5 存储层

`raw_persistence_failure`通过注入式Writer失败实现，不直接修改用户文件系统权限。

## 10. 故障计划

P1B已落地结构：

```text
FaultKind          # weak_signal / no_contact / saturation / drift / motion / ...
FaultWindow
- kind
- start_s
- end_s
- affected_channels   # pulse / load / ppg
- parameters          # 有序元组，禁止无约束 dict[str, Any]
SignalFaultInjector
- effective_ppg_delay_ms(tick)
- apply_value_faults(tick, pulse, load, ppg)
```

规则：

- 起止区间采用半开区间`[start, end)`；
- 默认窗口为会话时长的`[25%, 75%)`；
- 同通道冲突重叠在启动前失败；
- `insufficient_duration`不使用FaultWindow，仅缩短`duration_s`；
- P1B不写`events.jsonl`（留给P1D）；
- 削顶最后执行，`clipping`由最终值语义决定；
- PPG错位只改观察时延，不改样本时间戳、不改BeatTimeline。

`no_contact`契约表达（不扩展SensorStatus）：

- Pulse/Load/PPG均保持`connected`；
- Pulse逼近基线、无有效脉动；
- Load处于近零接触区；
- 不用`disconnected`/`read_failed`/`null`冒充无接触。

## 11. M1Sample构造

`M1SampleFactory`负责把时钟、通道观测和设备状态组装为M1-P0契约。

要求：

- 缺失使用`null + status`，不用0表示缺失；
- `source_type=simulator`；
- 场景和版本追溯通过会话级manifest及样本允许字段表达；
- 接收完整性字段由传输层适配结果生成；
- 每条样本可在测试模式下通过M1 Sample Schema；
- 正式生成可采用批量验证优化，但不得关闭验收验证。

## 12. SessionRecorder

职责：

1. 创建临时会话目录；
2. 先写场景和配置；
3. 流式写`samples.jsonl`和`events.jsonl`；
4. 计算计数、统计和哈希；
5. 生成`manifest.json`、`expected.json`和`summary.json`；
6. 成功后原子重命名为最终目录；
7. 失败时保留可识别的失败目录和已写证据。

### 12.1 写入失败

使用Writer接口：

```python
class SessionSink(Protocol):
    def write_sample(self, sample: M1Sample) -> None: ...
    def write_event(self, event: dict) -> None: ...
    def finalize(self, manifest: dict) -> None: ...
```

测试实现`FailingSessionSink`在指定写入次数失败。

## 13. ReplayDataSource

重放流程：

```text
读取manifest
→ 验证source和文件角色
→ 逐行读取samples.jsonl
→ 反序列化M1Sample
→ Schema/运行时验证
→ 按原顺序yield
```

重放一致性至少验证：

- 样本数；
- 逐样本结构相等；
- 事件文件哈希；
- manifest配置摘要；
- summary内容哈希。

## 14. 场景注册表

唯一注册入口：

```python
SCENARIO_REGISTRY: dict[str, ScenarioDefinition]
```

要求：

- ID唯一且稳定；
- 注册时验证版本和默认配置；
- CLI列表、文档生成和测试参数化均从注册表读取；
- 不在多个模块复制场景清单；
- 不使用散落的`if scenario == ...`实现业务分派。

## 15. 预期结果与真值隔离

`expected.json`可以包含：

- 预期质量主类别；
- 原因代码；
- 是否允许分析；
- 后续I1预期动作；
- 应检测的完整性错误；
- 会话完成状态；
- attempt关系。

后续SP/INT测试可以读取`expected.json`做断言，但正式算法输入只能使用M1Sample、设备状态和允许的会话元数据，不能读取场景真值。

## 16. 依赖策略

首版优先复用：

- Python标准库；
- NumPy；
- M1-P0已有`jsonschema`测试能力。

不新增pandas、PyArrow、SciPy等依赖，除非P1实现遇到明确阻断并形成决策记录。

## 17. 关键不变量

1. 同一配置摘要对应唯一确定性输出；
2. Pulse和PPG共享BeatTimeline；
3. 三通道样本时刻一致；
4. 故障状态与数值一致；
5. 模拟器不输出正式质量判断；
6. Replay不重新运行随机模型；
7. 失败会话不标记为完成；
8. M1-P0契约不被静默修改；
9. 模拟值不成为真实阈值；
10. 所有输出明确标记为synthetic/not hardware validated。

## 18. 实现前评审清单

- [x] 公共数据源接口足够小且不泄漏模拟器细节；
- [x] RNG流派生稳定；
- [x] 时间戳算法无累积截断漂移；
- [x] BeatTimeline与观测故障分离；
- [ ] 故障层次和组合优先级明确；
- [ ] JSONL、事件和manifest职责不重叠；
- [ ] Writer失败可控且不会破坏开发环境；
- [ ] Replay不依赖模拟器版本重算；
- [x] expected真值不会进入正式算法输入；
- [x] 未引入真实硬件才能决定的参数。

## 19. M1-P1A实现记录

已落地模块：

- `config.py`：`ScenarioConfig`、通道配置、`configuration_digest`；
- `clock.py`：`DeterministicClock`；
- `timeline.py`：`BeatTimeline`与`derive_rng_streams`；
- `channels.py`：Pulse/Load/PPG正常观测；
- `datasource.py`：`SimulatorDataSource`；
- `scenarios.py`：仅注册`normal_high_quality`（P1A基线）。

## 20. M1-P1B实现记录

已落地增量：

- `scenario_ids.py`：已实现场景ID集合；配置只做格式校验，存在性由注册表负责；
- `faults.py`：`FaultKind`、`FaultWindow`、`SignalFaultInjector`；
- `scenarios.py`：`ScenarioDefinition` + 10个已实现场景（1正常 + 9信号/接触）；
- `timeline.py`：RNG增加第5路`artifact_rng`（前4路与P1A `spawn(4)`兼容）；
- `channels.py`：PPG支持`delay_ms`覆盖；
- `datasource.py`：每帧基础观测后注入故障，状态在`samples()`内重建以保证可重入。

P1B版本：`0.2.0-p1b`。正常场景默认仍写`0.1.0-p1a`以保持digest与波形回归。

P1B未实现：`recorder`、`replay`、`cli`、设备/传输/存储故障、多attempt、`events.jsonl`、`expected.json`。
